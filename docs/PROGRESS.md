## 2026-11-24 — M20 두 이미지 비교 ✅

- `C`: 비교 켜기/끄기. 지금 사진이 **A**로 고정되고 다음 사진이 **B**. `←` `→`(휠·넘김 전부)로 B만 바꿔 가며 비교. `Esc`·`C`로 끝
- `V`: 보기 방식 순환 — **나란히** → **슬라이드** → **차이**
  - 나란히: 화면을 반으로 나눠 A | B, 이름표
  - 슬라이드: 두 이미지를 겹치고 세로 경계선을 끌어서 비교 (경계선 근처에서 드래그하면 경계선, 그 밖에서는 이동)
  - 차이: 다른 픽셀만 빨간색(차이가 클수록 밝게), 같은 픽셀은 어두운 회색으로 형태만. `25.71% 픽셀 다름 · MAX 225` 또는 `똑같음`
- 확대·이동·회전은 두 이미지에 똑같이 적용. B는 A와 같은 너비로 맞춰서 그림 → 같은 화면의 스크린샷은 정확히 겹치고, 2배 내보내기도 1배 원본과 맞음. 차이 계산도 크기가 다르면 맞춰서 비교
- A는 다른 사진으로 넘어가도 디코딩 캐시에 고정. A가 지워지거나 옮겨지면 비교 종료
- 스크린샷용 `MUUD_SHOW=compare` / `compare-slider` / `compare-diff`
- 테스트 92 → 97개 (모드 순환, 같은 이미지·한 픽셀 차이·크기 다른 이미지 비교, 너비 맞춤, A 고정)

## 2026-11-24 — 자동 릴리스

- `main`에 푸시될 때마다 Release 워크플로가 `Cargo.toml` 버전을 읽어, 그 태그(`v0.4.0` 등)가 아직 없으면 테스트·빌드·패키징 후 태그와 GitHub 릴리스를 직접 만듦. 이미 있으면 아무것도 안 함
- 이유: 릴리스를 손으로 실행할 필요 없이, 버전을 올리는 커밋이 곧 릴리스. 받은 릴리스 파일로 실물 점검([CHECKLIST](CHECKLIST.md))
- 손으로 내는 방법(Run workflow, 태그 푸시)도 그대로 남김. 릴리스 두 개가 동시에 돌지 않도록 `concurrency`
- 주의: 버전은 내보낼 준비가 됐을 때만 올림
- 이 변경이 들어가면서 v0.4.0이 처음으로 자동 릴리스됨

## 2026-11-24 — M19 성능 측정 → v0.4.0 ✅

**zune-jpeg vs libjpeg-turbo** ([BENCHMARKS.md](BENCHMARKS.md))
- `bench/compare_libjpeg_turbo.py`: 같은 파일을 libjpeg-turbo 3.1(Pillow 경유, 앱에는 안 들어감)로 디코딩해서 비교

- **결정 필요:** libjpeg-turbo로 바꾸면 화면 크기 디코딩이 장당 ~300ms 빨라지지만 C 빌드(NASM·CMake)와 라이선스 정책 변경(IJG)이 따라옴. 지금은 순수 Rust 유지
- 실물 파일 측정은 [CHECKLIST](CHECKLIST.md)에 추가

**속도 회귀 CI** — 새 "Speed" 작업(windows-latest): 32.5MP JPEG 원본·화면 크기 디코딩, 축소를 5회 중앙값으로 재고 같은 프로세스의 보정 루프 시간으로 나눈 비율을 `bench/baseline.txt`와 비교, 30% 넘게 느려지면 실패. 결과는 실행 요약과 공개 주석으로 표시. 빌드 시간을 줄이려고 `bench-ci` 프로필(릴리스 최적화, LTO 없음)

- 앱이 직접 한 휴지통·이동·이름 바꾸기·되돌리기는 이미 반영돼 있어서 중복 처리하지 않음
- 알림: `새 이미지 · 3`, `파일이 지워졌어요`
- 테스트 +5 (추가·삭제·이름 변경·내용 변경 구분, 애매한 이름 변경, 실제 폴더 감시, 보던 사진 유지·다음 사진·빈 폴더)

## 2026-11-24 — M15 색 프로파일 (ICC) ✅

- 라이브러리 선정: **moxcms** (순수 Rust, BSD-3-Clause OR Apache-2.0). qcms는 MPL이라 제외, LittleCMS(lcms2)는 MIT지만 C 빌드가 필요. moxcms는 이미 `image` 크레이트가 쓰고 있어서 새로 들어오는 코드가 없음 (`cargo deny` 통과)
- JPEG(zune-jpeg)·PNG·WebP·TIFF에 들어 있는 ICC 프로파일을 읽어 sRGB로 변환. 아이폰 Display P3, 카메라 Adobe RGB 사진이 원래 색으로
- 이름에 sRGB가 들어간 프로파일, 회색조·CMYK 프로파일(디코더가 이미 RGB로 바꾼 뒤라 맞지 않음), 읽을 수 없는 프로파일은 건드리지 않음
- 축소가 끝난 픽셀에 적용해서 빠름: 32.5MP 화면 크기 +25ms, 원본(확대 시) +270ms. 반투명 이미지는 프리멀티플라이를 풀고 변환
- 설정 → 보기 → 색 프로파일 켜기/끄기 (기본 켜짐), 바꾸면 다시 디코딩
- 정보 패널에 `ICC Display P3 → sRGB`

테스트 78 → 82개 (P3 변환·회색 유지·sRGB 무시, 투명도 유지, PNG에 넣은 P3 프로파일 변환·끄기, 표시 문구)

## 2026-11-24 — M14 큰 이미지 타일 ✅

- 버그 예방: `Ctrl+C`/`Ctrl+Alt+C`가 화면 크기 텍스처나 타일 미리보기를 복사하지 않도록, 텍스처가 복사에 필요한 크기보다 작으면 원본을 다시 디코딩
- 확인: 20,000 × 3,000 파노라마 JPEG를 가상 화면 100%로 캡처 → 5 타일, 선명

## 2026-11-24 — M13 디코딩 파이프라인 v2 ✅

**읽기 단계 분리** — 읽기 전용 스레드가 진행 방향으로 다음 10장(+뒤로 2장)의 파일 바이트를 미리 메모리에 올려둠(최대 512MB). 디코더는 메모리에 있으면 그걸 쓰고, 없으면 기다리지 않고 직접 읽음. 읽기 스레드가 지금 읽고 있는 파일은 디코더가 두 번 읽지 않고 기다림(NAS에서 같은 파일을 두 번 받지 않게)

**코어 수만큼 디코딩** — 디코더 스레드: 코어 − 1(2~7개) → 코어 수(2~16개). 읽기는 별도 스레드

**키를 누르고 있으면 건너뛰기** — 넘김 키가 반복 입력되면(키 누름 상태) 지금 위치만 디코딩하고 미리 읽기를 멈춤. 지나간 사진은 대기열에서 빠지고, 화면에는 지나온 사진 중 가장 최근에 디코딩이 끝난 것을 보여줘서 멈춰 보이지 않음. 키를 떼고 0.2초 뒤 평소대로

**화면 크기 텍스처 + 확대 시 원본**
- 캐시에는 모니터 크기(물리 픽셀)에 맞춘 이미지만 둠. EXIF 회전을 고려해 맞춤
- 화면 픽셀보다 크게 확대하면(100% 등) 현재 사진만 원본 해상도로 다시 디코딩해서 교체. 바이트는 읽기 캐시에 있으므로 디스크를 다시 읽지 않음. 다른 사진으로 넘어가면 원본은 해제
- 축소: k×k 블록 평균 → 고정소수점 면적 평균으로 정확한 크기 (image 크레이트 리사이즈 234ms → 자체 구현으로 교체)
- 측정(2코어 서버, 32.5MP 합성 JPEG, 2560×1440 모니터 기준): **장당 129.2MB → 12.4MB**. 원본 디코딩 340~390ms, 화면 크기 460~520ms (축소에 약 110ms 추가 — 대신 GPU 업로드가 1/10이고 같은 캐시에 10배 많은 사진이 들어감)

**기타**
- 진단 정보에 파이프라인 상태(디코더 수, 미리 읽은 파일 수, 원본 로드 여부, 키 누름 상태)
- 스크린샷용 `MUUD_SHOW=zoom100` (100%로 시작, 원본이 올라온 뒤 캡처)

테스트 64 → 75개 (화면 크기 계산·EXIF 회전, 블록 평균, 화면/원본 품질, 미리 읽기 캐시 순서·예산·정리, 10장 미리 읽기 목록, 키 누름 건너뛰기, 지나온 사진 표시, 원본은 현재 사진만, 확대 시 원본 필요 판단)
