## 2026-11-25 — 성능 검토 마무리: 릴리스 빌드 테스트 실패 수정

- v0.6.1 첫 릴리스 실행이 `cargo test --release`에서 실패 (CI의 디버그 테스트는 통과) → 새로 넣은 라이브러리 테스트가 화면 크기를 정하기 전에 디코딩이 시작되는 경쟁 상태였음. 릴리스 빌드는 디코딩이 빨라 먼저 끝나 버림. 화면 크기를 정한 뒤 시작하도록 고치고, 디버그 5회·릴리스 3회 반복 통과 확인. 태그가 만들어지기 전에 실패해서 잘못된 릴리스는 나가지 않음
- 이 과정에서 원본 보관이 실제 넘김에서는 거의 동작하지 않는 문제를 찾아 앞쪽 3장 보관으로 수정 (①에 반영)
- 테스트가 실패하면 실패한 테스트와 메시지를 CI·릴리스 실행의 공개 주석으로 남기도록 (로그는 로그인해야 보여서 원인을 바로 볼 수 없었음)

## 2026-11-25 — 성능 검토 ④: 썸네일 디스크 캐시 → v0.6.1 ✅

- **썸네일 캐시** — 만든 썸네일을 데이터 폴더 `thumbs/`에 작은 JPEG(투명하면 PNG)로 저장. 이름은 경로·크기·수정 시각의 해시(FNV-1a, 빌드가 바뀌어도 같은 값)라 파일이 바뀌면 자동으로 새로 만듦. 압축파일 항목은 압축파일의 크기·시각 기준
- EXIF 미리보기가 없는 32.5MP JPEG: 처음 352ms → 다시 열 때 **0.4ms**
- 256MB를 넘으면 오래된 것부터 지워 192MB로 (격자를 처음 열 때 백그라운드에서)
- **압축파일 열어 두기 보완** — 다른 폴더·압축파일을 열거나 닫으면 열어 둔 압축파일을 모두 닫음 → Windows에서 그 폴더를 옮기거나 지울 때 "사용 중"이 되지 않게

**성능 검토 정리 (①~④)**

| 항목 | 전 | 후 |
|---|---|---|
| 100% 확대 (현재·앞쪽 사진) | 원본 다시 디코딩 ~300ms | 디코딩 없음 (업로드만) |
| 축소해서 볼 때 GPU의 원본 텍스처 | 계속 유지 (~172MB) | 해제 |
| 격자에서 칸 이동 | 매번 5장 디코딩 + 10장 미리 읽기 | 없음 |
| 폴더 감시 (NAS) | 항상 2초마다 | 앞 2초 · 뒤 15초 · 최소화 멈춤, 정렬 시 파일별 조회 없음 |
| 미리 읽기 | 1개씩 | 2개 동시 |
| RAW 읽기 | 파일 전체 (30~60MB) | 헤더 + 미리보기 구간 |
| 압축파일 400항목 읽기 | 255.9ms | 1.2ms |
| 썸네일 다시 보기 | 장당 ~350ms (미리보기 없는 JPEG) | 0.4ms |

디코딩 자체 속도는 그대로(CI 속도 검사: 원본 214.5 → 213.9ms, 화면 크기 290.2 → 289.3ms) — 이번 개선은 같은 일을 반복하지 않게 한 것. 남은 큰 항목은 libjpeg-turbo 전환(화면 크기 디코딩 장당 ~300ms, 결정 필요, [BENCHMARKS.md](BENCHMARKS.md)).

테스트 127 → 129개 (썸네일 캐시 사용·파일 변경 시 새로 만들기, 오래된 것부터 정리). 버전 0.6.1.

## 2026-11-25 — 성능 검토 ③: NAS 읽기 (읽기 2개, RAW 부분 읽기, 압축파일 목차 캐시)

- **미리 읽기 동시 2개** — 읽기 스레드 1개 → 2개. NAS에서는 읽기 시간 대부분이 네트워크 대기라 두 파일을 동시에 받으면 미리 읽기가 거의 두 배 빨라짐. 서로 같은 파일을 읽지 않도록 "읽는 중" 목록을 공유
- **RAW는 미리보기까지만 읽기** — 표시에 쓰는 건 내장 JPEG뿐인데 파일 전체(30~60MB)를 읽던 것을: 앞 512KB(EXIF 포함)를 읽어 TIFF 디렉터리(썸네일 태그, JPEG 압축 스트립, SubIFD)에서 가장 큰 JPEG 위치를 찾고 그 구간만 읽음. 원래 위치에 놓은 버퍼라 EXIF 오프셋이 그대로 맞음. CR2·NEF·ARW·DNG·ORF·RW2·PEF·RAF 지원, 구조를 모르는 형식(CR3 등)은 예전처럼 전체 읽기
- **압축파일 목차 캐시** — 항목을 읽을 때마다 압축파일을 다시 열고 목차 전체를 파싱하고 이름을 하나씩 CP949 해석하던 것을: 최근 4개 압축파일을 열어 둔 채 이름→위치 표를 보관, 크기·수정 시각이 바뀌면 다시 엶. 400개 항목 전부 읽기 **255.9ms → 1.2ms** (로컬, 작은 항목 기준; NAS에서는 읽기마다 줄어드는 왕복이 더 큼)

테스트 126 → 127개 (두 읽기 스레드가 다른 파일을 고름, RAW 부분 읽기·같은 결과, 압축파일이 바뀌면 캐시 무효화)

## 2026-11-25 — 성능 검토 ②: 격자에서는 쉬기, 폴더 감시 줄이기

**썸네일 격자에서 큰 이미지 디코딩 멈춤** — 격자에서 화살표로 칸을 옮길 때마다 그 사진의 화면 크기 디코딩(주변 5장)과 미리 읽기(10장)가 돌던 것을, 격자가 열려 있는 동안은 아무것도 디코딩·미리 읽기 하지 않게. 격자를 닫으면 그 자리 사진부터 다시 시작. 썸네일 스레드가 CPU·디스크를 다 쓰게 됨

**폴더 감시 간격**
- 창이 앞에 있으면 2초, 다른 창 뒤에 있으면 15초, 최소화하면 멈춤. 다시 앞으로 오면 바로 한 번 확인 → 놓치는 변경 없이 NAS 폴더 목록 요청을 대부분 줄임
- 변경이 생겼을 때 "수정 시각·크기" 정렬을 다시 하면서 모든 파일에 정보를 다시 묻던 것(NAS면 파일 수만큼 왕복)을, 감시가 방금 받은 목록의 값으로 정렬

테스트 123 → 126개 (격자 중 작업 없음, 활동별 간격·목록 값 전달, 최소화 중 멈춤·복귀 시 즉시 확인)

## 2026-11-25 — 성능 검토 ①: 확대할 때 다시 디코딩하지 않기

검토(2코어 서버, 32.5MP 합성 파일) 결과 7곳을 고치기로 함 — 이 기록이 그 첫 번째.

**문제** — 화면 크기 디코딩도 JPEG 전체를 원본 해상도로 디코딩한 뒤 줄이는데, 그 원본 픽셀을 버렸다가 100%로 확대하면 같은 파일을 처음부터 다시 디코딩(약 300ms, CI 212ms)

**바꾼 것**
- 현재 사진과 진행 방향 앞쪽 3장은 디코딩하면서 만든 원본 픽셀을 버리지 않고 보관 → 확대하면 디코딩 없이 바로 원본 (업로드만). 추가 CPU 0, 메모리 상한 640MB(32.5MP 약 네 장, 넘으면 먼 것부터 버림). 뒤로 지나간 사진은 해제
  - 처음엔 현재·다음 두 장만 보관했는데, 앞으로 넘길 때 새 사진은 세 장 앞에서 디코딩되므로 현재가 될 때쯤엔 원본이 없어 효과가 거의 없었음 → ④ 릴리스 빌드 테스트가 실패한 것을 고치다 발견해 앞쪽 3장으로 확장
- 원본은 보관만 하고, 화면에는 확대가 필요할 때만 올림. 화면 크기 텍스처 해상도의 102%를 넘게 확대하면 원본으로, 90% 아래로 축소하면 다시 화면 크기 텍스처로 → GPU의 원본 텍스처(밉맵 포함 약 172MB)를 해제. 두 기준 사이 간격으로 깜빡임 방지
- 색 변환(ICC)을 한 사진, 타일이 필요한 큰 사진은 원본을 보관하지 않음(보관하려면 원본 크기 색 변환 270ms가 모든 사진에 들어가므로) → 확대 시 예전처럼 디코딩
- 검토하면서 원본 텍스처의 밉맵을 빼는 것도 고려했지만, 화면 크기~100% 사이(예: 50%)에서는 원본이 축소되어 그려지므로 밉맵이 없으면 자글거림 → 유지
- 버그 예방: 보관한 원본에 파일 크기·수정 시각이 빠져 상단 바가 `0 B`로 보이던 것을 화면 확인 중 발견해 수정

테스트 120 → 123개 (원본 픽셀 보관·PNG/JPEG, 로더가 원본→화면 순서로 전달·파일 정보, 현재·다음만 보관·확대 시 즉시·넘어가면 해제, 확대/축소 기준)

## 2026-11-25 — M28 회전 저장 ✅

- 임시 파일에 쓴 뒤 바꿔치기 → 중간에 실패해도 원본이 반쯤 써지지 않음. 저장 후 화면 회전은 0으로, 다시 디코딩
- JPEG가 아니면 안내, 압축파일 안에서는 막음
- 참고: DCT 계수를 직접 돌리는 jpegtran 방식은 EXIF를 무시하는 아주 오래된 프로그램용 — 필요해지면 검토

## 2026-11-25 — M27 포맷 ✅

- **SVG** — resvg로 렌더링. 벡터라서 보일 크기로 그림: 맞춤 보기는 화면 크기로, 확대하면 긴 변 2048px 이상으로 다시 그려 선명. 텍스트는 시스템 글꼴(처음 한 번만 읽음)
